## Findings

Verdict key: **verified** means re-checked against the source during this retro. **Reported** means it comes from a review lens and was not re-checked.

### Cross-story defects (the seams no single story saw)

1. **"Today" goes stale when the day rolls over, and the screens handle it differently.** Verified.
   - Source: `useTodayWornFitIds` is keyed `['todayWornFitIds', userId]` with no date (`lib/fits/wornFitIds.ts:72`).
   - Home refetches every wear read when the app returns from the background, and its comment explains why (`app/(tabs)/index.tsx:80-95`, 5.2/5.4).
   - The Planner, which added the same read in 5.6, only calls `setToday` on resume (`app/(tabs)/planner.tsx:155-161`), and no Planner test fires an AppState change.
   - Fit detail has no rollover handling at all (5.5).
   - The writes work out the date again when they run (`lib/fits/markFitWorn.ts:20,54`), so a screen showing yesterday writes or undoes against today.
   - Consequence: after an overnight resume, the Planner's today sheet and Fit detail show yesterday's wear as "Worn today". Undo asks "its photo will be deleted" and deletes nothing. Fit detail's Add tile can attach a photo to yesterday's wear.
   - Raised by: the verification-gap lens, edge-case #1–2, adversarial #1–2, and 5.5 triage #17 (`deferred-work.md:212`).
   - **Disposition:** fix now (action 1).
   - **Prevention:** one date-scoped "today" convention instead of each screen remembering to refetch.
2. **Fit detail kept its own worn toggle after 5.6 extracted a shared one.** Verified.
   - Source: `useWornTodayToggle` is used only by Home and the Planner (`grep`). Fit detail still has its own override and busy state (`app/fit/[id].tsx:156-167, 209-240`).
   - How it diverges:
     - On failure it pins the override (the hook deliberately doesn't).
     - Its guard skips `countingPhotos` and `deleting`, so the toggle can run during Delete's photo count, despite 5.5's "one lock" comment.
     - It holds no lock while the undo confirmation is open.
   - Raised by: adversarial #5, edge-case #9–10 and #16.
   - **Disposition:** fix now (action 2).
   - **Prevention:** when a story extracts a shared hook, its spec lists every existing copy (5.6's spec named only Home).
3. **Photo replace/remove act on the client's cached paths.** Verified in part.
   - Source: the row update is unconditional (`lib/fits/wearPhoto.ts:144`, `.eq('id', wearId)`), and afterwards the code deletes the files from the cached `WearRef.photo`.
   - Consequence: if the photo was replaced on another device, the new files are orphaned.
   - Raised by: adversarial #3, edge-case #14.
   - **Disposition:** defer. It depends on the orphan-cleanup job already deferred (`deferred-work.md:194`).
4. **Locks are per screen, so writes to the same wear can overlap across tabs.** Reported.
   - Starting a photo upload on Home, switching tabs, and undoing the same wear in the Planner isn't blocked, because each screen has its own `useWearPhotoActions`/`useWornTodayToggle` instance.
   - Raised by: adversarial #4 and #16, edge-case #6.
   - **Disposition:** defer. It needs a tab switch in the middle of an upload.
5. **Re-planning a day that was already worn hides that wear and its photo in the Planner.** Reported.
   - Source: the `wornOnDay` rule that "a planned Fit that wasn't worn wins" (`app/(tabs)/planner.tsx`). The 5.5 deep link passes only `date`, not `fitId`.
   - Raised by: adversarial #7, edge-case #5.
   - **Disposition:** defer. Settle it by planning a different Fit on a worn past day on a device.
6. **Deleting a Fit.** Verified.
   - `deleteFit` clears photos with one `.in('photo_path', …)` list (`lib/fits/deleteFit.ts:52`), so the URL grows with the number of photos.
   - `handleDelete` invalidates only `['fits']` (`app/fit/[id].tsx:257`), but every screen refetches on focus.
   - Raised by: edge-case #12–13, adversarial #12.
   - **Disposition:** defer. The `.in()` list only breaks at hundreds of photos on one Fit.
7. **Wear reads with no limit.**
   - Verified: the streak read selects every `worn_on` (`lib/fits/wearStreak.ts:17`), and so does `getWornFitIds` (`lib/fits/wornFitIds.ts:15`). Past PostgREST's maximum row count (1000) the streak would be truncated.
   - Reported: Home's loading gate waits on these reads.
   - Raised by: adversarial #9–11.
   - **Disposition:** defer, to Epic 6 (6.3/6.4 performance).
8. **Signed-URL expiry and signing errors.** Reported.
   - Screens that stay mounted for more than an hour may show expired URLs, and signing errors are neither classified nor reported.
   - Raised by: adversarial #14, edge-case #15.
   - **Disposition:** defer. Settle it by leaving a tab open for more than an hour on a device.
9. **No cleanup on the server side.** Verified in part.
   - `wear-photos` files are removed only by the client. Server-side row deletes and the `auth.users` cascade leave files behind.
   - Raised by: adversarial #15.
   - Already deferred (`deferred-work.md:194,202`).
   - **Disposition:** fold into Epic 6 (action 5).
