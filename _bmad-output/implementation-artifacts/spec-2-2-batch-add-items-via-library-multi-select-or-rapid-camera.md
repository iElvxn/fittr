## Intent

**Problem:** Story 2.1 only added items one at a time (single photo → review → save); cataloging a whole wardrobe this way is too slow to clear the epic's own "10 items in under 3 minutes" bar (NFR10).

**Approach:** Extend the existing single-item capture/review screen (`app/add-item.tsx`) and its store to hold an array of in-progress items instead of one, add a live rapid-camera view (`expo-camera`) and library multi-select as two new entry points that feed that same array, and process/upload/save every item in the batch through the exact single-item pipeline Story 2.1 already built (background removal, color detection, upload, insert) run once per item.

## Boundaries & Constraints

**Always:** the source-choice action sheet has exactly two options, upgraded in place — "Take Photo" opens the live rapid-camera view (any number of shots) and "Choose from Library" opens multi-select (any number of photos); single-item capture is simply the batch-of-one case of each, superseding Story 2.1's single-shot `captureFromCamera`/single-select `pickFromLibrary` rather than keeping them as a parallel path; the rapid-camera view requires an explicit "Review" tap to leave capture and enter the queue screen — never auto-advances after one shot; background removal for each batch item runs on-device sequentially, one item at a time (epic's Technical Decision), never in parallel, and starts as soon as that item's photo exists (per shot, or per picked library asset) rather than waiting for the whole batch, so processing overlaps with continued shooting/selection toward the <3-minute NFR; the rapid-camera filmstrip shows each shot's own processing state (spinner while pending, checkmark once its cutout is ready) so progress is visible during capture itself, not just at review; the queue/review screen shows each item as a compact row (thumbnail + status) with category/color/fields collapsed by default and expandable per row on tap, to keep a 10-item batch scannable rather than showing every control open at once; a single "Save all" button (disabled + spinner while saving, matching the existing `Button loading` pattern) stays disabled until every item is `ready`; each item is individually retakeable/correctable before the batch saves, per the AC; each item also has a direct "remove from batch" action (a small button, not a swipe gesture) with no confirmation step -- unlike deleting a *saved* wardrobe item elsewhere in the app, this discards an unsaved, trivially-redoable photo, so a confirmation dialog would be pure friction; removing the batch's last remaining item backs out of the screen entirely, matching the "nothing captured" empty state; each collapsed row shows a chevron (▾ collapsed / ▴ expanded) as a visible tap-to-edit affordance, and renders as a `surface-raised` card (`rounded.md`, tonal-difference elevation per DESIGN.md, no drop shadow) rather than a flat hairline-divided list row; there is no hard cap on batch size, but a non-blocking counter/soft-warning appears past ~20 items in progress, never blocking capture or selection; batch save attempts every item in order and, on any item's failure, makes a best-effort rollback (delete) of items already saved in that attempt, leaving the review screen with everything intact for retry — this rollback is best-effort, not guaranteed, since a genuine connectivity loss can make the rollback's own delete calls fail the same way the original save did; a later successful retry is always safe regardless, since every item's client-generated `itemId` upserts rather than duplicating; each item keeps its own client-generated `itemId` and goes through the unchanged `uploadItem`/`insertWardrobeItem` from 2.1 (same upsert idempotency, same Storage path convention, same `wardrobe_items` table/RLS — no schema change); `trackItemAdded` fires once per saved item and carries `batchSize` (epic's `item_added` event shape: source, category, batch_size); camera permission reuses the existing `NSCameraUsageDescription` copy and the existing `WardrobeItemError('permission_denied', CAMERA_PERMISSION_MESSAGE)` pattern; the shutter button and any per-row icon actions stay ≥44×44pt and inside safe-area insets, consistent with the rest of the app.

**Never:** a server-side or queued batch job — stays client-driven and synchronous, same no-offline-layer architecture as 2.1; parallel background removal across items; any change to `wardrobe_items` schema, RLS policies, or the Storage path convention — this story only calls the existing per-item save path more than once; a reprocessing feature for a poor cutout — retake only, same as 2.1; a hard block on batch size; a swipe-to-delete gesture for removing a batch item — consistent with the app's existing rule against swipe-to-delete elsewhere; a confirmation step before removing a batch item — that rule is specifically for deleting a *saved* wardrobe item (Story 2.4), not an in-progress, unsaved photo; auto-advancing out of the camera view after a single shot.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Happy path, rapid camera | Open camera, take 5 shots, tap Done, review all 5, Save | Camera stays open across shots; filmstrip grows by one thumbnail per shot; review screen shows all 5 with independent status; all 5 rows inserted, all 10 files uploaded | N/A |
| Happy path, library multi-select | Choose from Library, pick 6 photos | Each photo enters the same queue/review screen as rapid camera; Save inserts 6 rows | N/A |
| One item's cutout is poor | Review screen, tap Retake on item 3 of 5 | Only item 3 restarts capture from its original source; items 1,2,4,5 keep their state untouched | N/A |
| One item fails processing | Background removal finds no subject for item 2 | Item 2 shows the existing "Couldn't find your item..." message inline with a per-item Retake; other items remain `ready`/`processing`; Save stays disabled until item 2 is resolved | Same copy as 2.1's single-item case |
| No connection at batch save | Save tapped while offline, partway through the 5-item upload loop | Best-effort rollback deletes already-uploaded items in this attempt; if connectivity is genuinely down, those deletes can themselves fail silently, so some items may already be saved. A later successful retry is always safe -- the same client-generated item IDs upsert, never duplicating. User stays on review screen with all 5 items' cutouts/fields intact either way | "No connection — nothing was lost. Try again." + retry action |
| User backs out mid-batch | Dismiss add-item screen before Save, batch has 3 items in progress | No Storage writes, no row inserts for any of the 3; no orphaned state | N/A |
| Single item via either entry point | Rapid camera with exactly 1 shot, or library multi-select with exactly 1 photo | Same review/save path as a batch of 5 — behaves as the degenerate batch-of-one case | N/A |
| Batch grows large | 21st photo captured/selected in one session | A non-blocking counter/soft-warning appears; capture/selection is not blocked | N/A |
| Remove one item from a multi-item batch | Batch of 5, tap Remove on item 3 | Item 3 disappears immediately, no confirmation; items 1,2,4,5 keep their state and order; Save remains gated on the remaining items' readiness | N/A |
| Remove the only item in the batch | Batch of 1, tap Remove | Batch becomes empty; screen backs out, matching the "nothing captured" case | N/A |

**Acceptance Criteria:**
- Given a batch of 5 items via rapid camera, when Save completes, then 5 `wardrobe_items` rows exist and 10 Storage objects (cutout+thumb per item) exist, each with correctly-paired `itemId`-scoped paths.
- Given a batch save that fails partway (simulated no-connection after 2 of 5 items uploaded), when the failure occurs, then those 2 items' Storage objects and rows are removed and zero rows/objects from this batch persist.
- Given a batch of 1 item via either entry point, when Save completes, then behavior matches 2.1's existing single-item outcome exactly (one row, `batchSize: 1` on the analytics event).
- Given the rapid-camera view with at least one shot taken, when the user has not tapped "Review", then the camera stays open and no navigation to the queue screen occurs.
- Given a batch of 3 items, when the user removes item 2 without expanding it, then only item 2 disappears from the queue and Save's readiness gate is recomputed against the remaining 2.

## Implementation Notes

- `stores/wardrobeCapture.ts`: implemented as `addCaptured(source, photoUri) -> id`, `setItemProcessed`, `setItemProcessingFailed`, `replaceItemPhoto` (the retake action -- named for what it does: swap in a new photo and drop back to `processing`), per-item field setters, `toggleExpanded`, `reset`. No separate `startBatch` action was needed -- `addCaptured` on an empty `items` array *is* starting a batch.
- `lib/wardrobe/capture.ts`: `PickWardrobePhotoResult` renamed `PickWardrobePhotosResult` (`{ uris: string[] }`) since even a one-photo library pick now returns an array; `captureFromCamera` removed entirely, no longer re-exported from anywhere.
- `lib/wardrobe/rapidCamera.ts`: `expo-camera`'s standalone `requestCameraPermissionsAsync`/`getCameraPermissionsAsync` exports exist in the compiled JS but are **not** part of the package's public TS API surface -- only reachable via the `@hidden` `Camera.requestCameraPermissionsAsync()` object, which is what 2.1's `captureFromCamera` pattern needed here too. `capturePhoto(cameraRef)` takes a `RefObject<CameraView | null>` rather than the view itself, so it can be unit-tested with a plain mock ref instead of rendering a `CameraView`.
- `lib/wardrobe/addItem.ts`'s `saveBatch()`: on failure, the failing item's own Storage objects are cleaned first (its `uploadItem` can have already succeeded even though its `insertWardrobeItem` didn't -- `uploadItem` only rolls back *its own* cutout/thumb pair, not a downstream insert failure), then every earlier fully-committed item is rolled back (Storage + row). Supabase's Postgrest query builder is thenable but not a real `Promise` (no native `.catch`); rollback deletes wrap it in `Promise.resolve(...).catch(() => {})` so a failed best-effort rollback can never mask the original error.
- `app/add-item.tsx`: local `mode` state (`choosing | camera | reviewing | permission-error`) replaces the store's old single `status`, since status is now per-item. Camera-sourced retake re-enters `camera` mode for exactly one replacement shot (tracked via a local `retakingId`) then returns straight to `reviewing`; library-sourced retake relaunches the (now multi-select) picker and uses only the first picked uri, ignoring any extras -- simpler than a dedicated single-select call, and a user picking more than one during a retake is a narrow, self-inflicted case. `trackItemAdded` is called once per item in the loop after a successful `saveBatch`, each carrying the batch's total size.
- No automated screen-level test exists for `app/add-item.tsx` -- matches Story 2.1's own precedent (its Review Triage Log notes two bugs were only catchable on-device, not via lint/typecheck/unit tests) given the screen's `ActionSheetIOS`/`CameraView`/`ImagePicker` native-module entanglement. The Verification section's manual checklist was written to walk every I/O matrix row explicitly as a substitute.
- Remove/chevron/card-aesthetic pass (human-requested after initial completion): `removeItem(id)` is a plain filter on the store's `items` array, available regardless of an item's status. `BatchQueueRow`'s remove "×" sits outside the expand-toggle `Pressable` (a sibling in the same row, not nested inside it) so tapping it never also fires `onToggleExpand`. `app/add-item.tsx`'s `handleRemove` checks `items.length <= 1` *before* calling `removeItem`, backing out of the whole screen instead of removing into an empty, permanently-`disabled`-Save queue.
- Second aesthetic pass (human-requested: "make the icons bigger... aesthetic and fashion styled"): a generic `--design-system` search for "fashion" returned a rose/gold, Inter-based web-SaaS palette -- not used, since it directly contradicts this app's own deliberate, already-frozen monochrome system (`DESIGN.md`: "no chromatic color anywhere in the chrome"). Instead leaned harder into the app's existing serif/sans editorial pairing: the chevron/"×"/filmstrip-badge glyphs were sized up (14px→20-24px) since they were riding the small `label` text size, too subtle to read as real icons; the collapsed category label switched from `body` to the serif `title` font for a catalog-entry feel; "Category"/"Color" section labels (uppercase, tracked-out) were reinstated above their control groups, matching Story 2.1's original single-item screen structure that got dropped when this was extracted into `BatchQueueRow`; thumbnail sizes increased (72→88px in the queue, 56→64px in the filmstrip) to give the photography -- DESIGN.md's stated "real content" -- more presence.

## Spec Change Log

- 2026-09-16: Human renegotiated the frozen "No connection at batch save" matrix row and its corresponding Boundaries clause, from an absolute "no net rows/objects persist" guarantee to a best-effort one. Reason: review found `saveBatch`'s rollback deletes are themselves network calls wrapped in `.catch(() => {})`; under a genuine connectivity loss (as opposed to some other failure), those rollback calls fail silently the same way the original save did, so the literal zero-persistence promise cannot hold in that specific case without a local-first queue or retry-on-reconnect mechanism -- both explicitly excluded by this epic's own frozen Technical Decisions ("No local-first save step," "no silent background queue"). No code changed: the existing best-effort rollback plus per-item upsert idempotency (a later retry is always safe, never duplicates) was judged sufficient, matching this app's precedent of accepting narrow, low-harm gaps elsewhere (Story 2.1's accepted app-killed-mid-flow orphan case) rather than building new infrastructure for a rare, self-healing edge case.
- 2026-09-16: Human requested and authorized reopening the frozen "retake only, no separate remove-from-batch action" decision, plus a discoverability/aesthetic pass on the queue screen. Reason: user-requested feature the original Open Questions resolution had deliberately excluded to limit scope, not a defect being reversed. Added: a per-item remove action (button, not swipe, no confirmation -- distinct from Story 2.4's saved-item delete, which does require confirmation), a chevron disclosure indicator, and a card-style restyle of `BatchQueueRow` per `DESIGN.md`'s existing tonal-elevation/`rounded.md` conventions. KEEP: swipe-to-delete stays prohibited (unchanged app-wide rule); the earlier "false" Review Triage Log verdict on this exact gap is not edited (it correctly described the intent as it stood at that time) -- this entry supersedes it going forward.

## Review Triage Log

Three parallel layers ran against the diff since baseline: Blind Hunter (12 findings), Edge Case Hunter (8 findings), and a Verification Gap pass (2 gap findings + 1 other). Overlapping findings sharing a root cause are merged into one row.

- **Cancel in camera mode during a retake discards the whole batch, not just the retake** (edge-case-hunter) — `high` — confirmed: the camera-mode Cancel button always calls `router.back()` unconditionally, never checking `retakingId`; backing out of a single item's retake unmounts the screen and `reset()` wipes every already-reviewed item in the batch. Route: `patch` — if `retakingId` is set, Cancel should clear it and return to `reviewing` instead of calling `router.back()`.
- **Library multi-select processes every picked photo's background removal in parallel, not sequentially** (verification-gap "other finding") — `high` — confirmed: `handleChooseLibrary`'s `result.uris.forEach(...)` fires `void processItem(id, uri)` for every photo with no `await` between iterations, directly violating this spec's own frozen Boundary ("background removal for each batch item runs on-device sequentially... never in parallel") and the epic's stated rationale (thermal/memory pressure from concurrent Vision calls). Route: `patch` — process picked photos with a sequential `for...of` + `await` loop instead of `forEach` + `void`.
- **Batch-save rollback's own network calls are silently swallowed, so under the exact no-connection scenario the frozen I/O matrix describes, already-committed items may not actually be removed** (edge-case-hunter) — `high`, **intent_gap** — confirmed: `saveBatch`'s rollback wraps its Storage `remove` and row `delete` calls in `.catch(() => {})`; if the triggering failure was a genuine connectivity loss, those same rollback calls fail too, silently. The frozen matrix's literal claim ("No net rows/objects persist... already-uploaded items in this attempt are rolled back") cannot hold in that exact case without either a local-first queue or an eventual-consistency retry — both of which the epic's own frozen Technical Decisions explicitly rule out ("No local-first save step," "no silent background queue"). The existing per-item `itemId` upsert idempotency means a *successful* later retry self-heals (no duplicates), but a user who abandons the batch after a no-connection failure without retrying will find some items already visible in their wardrobe despite being told nothing was saved. This is a genuine conflict inside the frozen block requiring a human decision, not something the agent can resolve unilaterally.
- **Shutter capture failure gives no user-facing feedback at all** (blind-hunter + edge-case-hunter, same root cause) — `medium` — confirmed: `handleShutterPress`'s catch only does `console.error`/`Sentry.captureException`; no `setFieldError` or any visible state change, so a failed shutter press looks like nothing happened. Route: `patch` — show an inline error in camera mode on capture failure.
- **No re-entrancy guard on the camera shutter** (edge-case-hunter) — `medium` — confirmed real: two overlapping `capturePhoto()` calls (a fast double-tap) can race, and specifically during a retake the second call can read `retakingId` after the first already cleared it, silently turning an intended retake into an unrelated new batch item. Route: `patch` — add a `capturingRef` guard so a shutter tap is ignored while a capture is already in flight.
- **`KeyboardAvoidingView` was dropped for the reviewing screen** (edge-case-hunter) — `medium` — confirmed deletion regression: the removed single-item screen wrapped its scroll content in `KeyboardAvoidingView`; the new reviewing-mode return has no equivalent, so the keyboard can cover an expanded row's Name/Brand/Notes field, especially lower in a long batch. Route: `patch` — re-wrap the reviewing-mode return.
- **`handleSaveAll` casts `itemId`/`cutoutUri`/`thumbUri` as non-null with no runtime guard** (blind-hunter + verification-gap, same root cause) — `low` — confirmed: the old single-item `handleSave`'s defensive completeness check (`if (!cutoutUri || !thumbUri || !itemId || !source) return;`) has no batch equivalent; only the render-level `allReady` gate protects `saveBatch` from a not-ready item, with no defense-in-depth inside the function itself. Not currently reachable via any UI path, but a future regression in `allReady` would ship silently (no test catches it either). Route: `patch` — add a one-line guard re-checking readiness inside `handleSaveAll` before calling `saveBatch`.
- **Inconsistent Sentry/console logging convention across the new catch blocks** (blind-hunter) — `low` — confirmed: `processItem`/`handleSaveAll` correctly guard logging with `!(error instanceof WardrobeItemError)`; `handleShutterPress` logs unconditionally (over-reports expected cases), `handleChooseCamera` never logs at all (under-reports genuine bugs). ## Design Notes

- The store's array model treats single-item as batch-of-one rather than keeping two parallel shapes — this is what lets `add-item.tsx` stay one screen for both cases, per 2.1's own Design Notes anticipating this story.
- Sequential-not-parallel background removal across items is an explicit epic Technical Decision (not this spec's invention) — the Vision-backed removal module is CPU-heavy per call, and running several concurrently on a phone risks thermal throttling or memory pressure worse than the sequential wait.
- Two-option action sheet (upgrade-in-place) over four: fewer near-duplicate choices reduces the decision the user has to make at the entry point, consistent with the app's own minimal/consistency-first design language.
- Collapsed-by-default queue rows, expand-on-tap: showing category chips + color swatches + three text fields open for every row in a 10-item batch would overwhelm the screen at once; per-item detail is progressive disclosure instead.
- Per-shot processing status in the filmstrip (spinner -> checkmark) exists so the multi-step async pipeline is never silent — a bare wait with no feedback until the very end reads as broken, not just slow.
- No hard batch-size cap, only a soft/non-blocking counter past ~20: a hard wall blocks a legitimate large capture session for a marginal, self-mitigating memory concern (cutouts are typically well under a device's available memory even at 30-40 in flight).
- Remove needs no confirmation, unlike Story 2.4's saved-item delete: that rule protects against losing persisted data via an accidental native action-sheet-free swipe; nothing here is persisted yet, and removing a photo you didn't mean to is trivially undone by recapturing/re-picking it.
- Chevron (▾/▴) plus a real card background (rather than a flat hairline-divided row) makes each row's tappability legible without new copy -- a visible, tonal-shift "card" reads as interactive the way a plain list row bounded only by a 1px hairline doesn't.

## Verification

**Commands:**
- `npm test -- wardrobeCapture capture rapidCamera addItem batchQueueRow` -- expected: all new/extended unit tests pass.
- `npx tsc --noEmit` -- expected: no type errors.

**Manual checks (if no CLI):** `app/add-item.tsx` itself has no automated screen-level test -- consistent with Story 2.1, its native-module entanglement (`ActionSheetIOS`, `CameraView`, `ImagePicker`) is verified on-device rather than through heavily-mocked component tests; every underlying module it composes (store, capture, rapid-camera, batch save/rollback, queue row) has full unit coverage instead. On a physical iOS 17+ device via the EAS dev build, walk every I/O matrix row:
- Rapid camera: take 5 shots (filmstrip fills, each shot's status updates live), tap Review, confirm all 5 show independently in the queue, Save inserts 5 rows + 10 Storage objects.
- Library multi-select: pick 6 photos, confirm the same queue screen, Save inserts 6 rows.
- Retake one item mid-batch in each batch type; confirm only that item resets, others keep their state.
- Force one item's background removal to fail (photo with no clear subject); confirm its inline error + Retake, other items unaffected, Save stays disabled until resolved.
- Trigger a no-connection failure during Save (airplane mode mid-batch); confirm no rows/objects persist and the retry keeps all items intact.
- Back out of an in-progress batch; confirm no Storage writes or row inserts occurred.
- Add exactly 1 item via each new entry point; confirm it behaves identically to 2.1's single-item outcome.
- Capture/select past 20 items; confirm the soft counter appears and nothing is blocked.
- Remove one item from a multi-item batch (no confirmation prompt), then remove the last remaining item and confirm the screen backs out.
