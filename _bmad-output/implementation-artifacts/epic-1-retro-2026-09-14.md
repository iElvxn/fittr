### Security review (explicit focus per user request)

**Wins, verified directly:**
- No secrets committed anywhere in the epic's tracked files (scanned for Supabase key shapes, Google API key shapes, and PEM private-key headers — zero matches). `.env.example` holds only empty placeholders with an explicit comment warning against prefixing `SUPABASE_SERVICE_ROLE_KEY` with `EXPO_PUBLIC_` (which would ship an RLS-bypass credential to every client). `.env.local` is gitignored.
- RLS is applied consistently and correctly across both tables/buckets the epic touches: `profiles` (explicit per-operation SELECT/INSERT/UPDATE policies, no DELETE) and the newer `wardrobe` Storage bucket (SELECT/INSERT/UPDATE scoped to the caller's own uid-prefixed folder, no DELETE) — same pattern, applied twice, both automated-tested via `supabase/tests/rls.test.ts`'s cross-user checks (skipped without live credentials, never silently passing).
- Apple/Google identity tokens are verified server-side via Supabase's own `signInWithIdToken` in both cases — no custom trust logic anywhere in the epic.
- Session storage never uses unencrypted `AsyncStorage` — verified the hybrid adapter in `lib/supabase.ts` still encrypts with an `expo-secure-store`-held AES key.

**Gap found:** `profiles_update_own` (`supabase/migrations/0001_profiles.sql:49-55`) is `USING (id = auth.uid()) WITH CHECK (id = auth.uid())` with no column-level restriction — RLS constrains which *row* a client can touch, not which *columns*. `username` is documented everywhere (the migration's own comment, `epic-1-context.md`) as "system-generated, immutable, never user-supplied," but nothing at the database layer actually enforces that: any signed-in user can call `supabase.from('profiles').update({ username: '...' }).eq('id', <own-id>)` directly through the same publishable-key client the app itself uses, bypassing the app's own `updateProfile()` (which never sends `username`) entirely. Low likelihood of exploitation today (username isn't surfaced or valuable to attack yet), but it is a real, verifiable gap between a documented invariant and what the database actually enforces — worth closing before Epic 2+ gives usernames more surface area.

### Diff-scope review (`bmad-review`: adversarial, edge-case-hunter, verification-gap, run over the full epic diff, weighted toward story boundaries and security)

**[HIGH, fix now] Sentry and PostHog have likely never actually activated in any real build.** `lib/observability/sentry.ts:3` and `lib/analytics/posthog.ts:3-4` read `process.env.SENTRY_DSN` / `POSTHOG_API_KEY` / `POSTHOG_HOST` with no `EXPO_PUBLIC_` prefix. Expo only inlines `EXPO_PUBLIC_`-prefixed variables into the client bundle (verified: no custom babel/metro env-inlining plugin exists in `babel.config.js`/`metro.config.js` to override this default). The shell-level `env: export ... POSTHOG_API_KEY POSTHOG_HOST SENTRY_DSN` line the Expo CLI itself prints is the CLI tooling process seeing the var — not proof it reaches the actual app bundle running on a device. Consequence: `dsn`/`apiKey` are `undefined` in every real build regardless of what's in `.env.local`; PostHog's own code explicitly calls `posthog.optOut()` whenever `apiKey` is falsy (`lib/analytics/posthog.ts:16-17`), so `trackSignedUp` has been a guaranteed no-op since Story 1.1. This directly contradicts the epic's own declared acceptance bar ("a test analytics event reaching PostHog") and all three stories' verification notes, which believed this was wired and working — no single session questioned it because each trusted the previous one's "already wired" note. *Disposition: fix now (rename the three env vars to their `EXPO_PUBLIC_` forms everywhere they're read/written — code, `.env.example`, CI secrets — and re-verify with a real event reaching the PostHog dashboard). Process lesson: "wired against placeholder env vars, nothing to verify yet" was accepted at face value for two more stories; a wiring claim like this needs one real end-to-end check before it's trusted, not just a code read.*

**[MEDIUM, fix now] Real email/password sign-up (the one flow explicitly documented as fully device-testable today) dead-ends when "Confirm email" is on.** Confirmed independently by all three lenses plus this session's own live device testing. `lib/auth/emailSignUp.ts`'s `signUpWithEmail` never checks `data.session`; `email-sign-up.tsx` unconditionally routes to `/onboarding`; `onboarding.tsx` has no session guard (unlike `(tabs)/_layout.tsx`, which redirects to Welcome when session drops); `handleContinue`'s `if (!userId) return;` silently no-ops with zero feedback. Compounding: Story 1.2 removed onboarding's only other exit (the `__DEV__`-only sign-out button), so an affected user has no way off the screen at all. Already logged in `deferred-work.md` (commit `a367221`) from this session's live testing, but still unfixed. *Disposition: fix now — branch on `data.session` after sign-up; if absent, show a "check your email to confirm" state instead of navigating to onboarding, and add a session guard to `onboarding.tsx` matching the `(tabs)` pattern.*

**[MEDIUM, fix now] `profiles` has no database-level enforcement for three invariants its own migration comments document as guaranteed.** `profiles_update_own`'s RLS (`0001_profiles.sql:49-55`) is `USING/WITH CHECK (id = auth.uid())` — it restricts *which row*, never *which columns*. Three separate consequences, same root cause: (1) `username`, documented as "system-generated/immutable," can be changed by any user calling the Supabase client directly, bypassing `updateProfile.ts`'s discipline entirely; (2) `avatar_path` can likewise be set to an arbitrary string (storage RLS still blocks reading someone else's actual file, so this doesn't leak images today, but it breaks the "always my own path" invariant other code assumes); (3) `display_name`'s non-blank/50-char cap exists only in `lib/profile/validation.ts`, client-side. *Disposition: fix now — either a `BEFORE UPDATE` trigger rejecting `username`/`created_at` changes plus a `CHECK` on `display_name`, or column-privilege `REVOKE`/`GRANT` scoping `UPDATE` to exactly `display_name, avatar_path, updated_at`. Worth doing before Epic 2 gives any of these columns more real surface area.*

**[LOW, defer] `handleSignOut` ignores `supabase.auth.signOut()`'s error result.** `app/(tabs)/profile.tsx:44-47` always navigates to Welcome regardless of outcome; only the success path is tested. An offline sign-out may leave a still-valid server-side session while the UI claims the user is fully signed out. *Disposition: defer — real but narrow (shared/handed-down-device scenario), and the fix (branch on the error, decide what "offline sign-out" should mean) is a small product decision, not a pure bug fix.*

**[LOW, accept-as-is / forward note for Epic 6] Deleting an account leaves its avatar object orphaned in Storage.** `profiles.id` cascades on `auth.users` delete; nothing removes the matching `wardrobe/{uid}/avatar.jpg`. Not this epic's problem — account deletion is explicitly Epic 6 — but worth flagging now so Epic 6's service-role deletion flow builds the storage cleanup in from the start rather than discovering the gap later.

**[LOW, accept-as-is] `profile.tsx`'s query-error branch always shows "Check your connection," even for a non-connectivity failure.** Same tradeoff Story 1.2's own review already considered and accepted ("the only realistic failure mode today"); Story 1.3 widened the query and added more error surfaces (Storage, signed URL) without revisiting that call. Still reasonable today, but the surface area backing the assumption grew — noted so a future retro doesn't have to re-derive this, not routed as a new defect.

**[LOW, accept-as-is] Minor hygiene notes, no action needed now:** `providerDisplayName.ts`'s try/catch only catches thrown errors, not Supabase's resolved-`{error}` shape — currently harmless (outcome is "do nothing" either way) but a landmine if the pattern is copied somewhere the error actually matters; `isNewAccount`'s 2-second new-vs-returning threshold has no boundary test and a slow first sign-in could misclassify a new account as returning (sends them straight to Home, permanently skipping onboarding — same "no completion flag" gap already tracked); `.npmrc`'s repo-wide `legacy-peer-deps=true` silently suppresses all peer-conflict signals rather than scoping to whichever dependency needed it; the Google iOS URL scheme is hardcoded in `app.json` while its source client ID is a self-supplied env var, an easy-to-miss sync point for a future contributor.

**Checked and refuted:** the adversarial lens raised a CI-secrets exfiltration concern (a same-repo PR modifying `rls.test.ts` to log `SUPABASE_SERVICE_ROLE_KEY`) — verified against `.github/workflows/ci.yml`: the workflow triggers on plain `pull_request` (not `pull_request_target`), so GitHub's default protection already withholds repo secrets from fork PRs. The narrower, real part of that finding stands as a low note: no CI-vs-production Supabase project separation is documented anywhere, so CI's RLS test creates/deletes real throwaway accounts against whatever project the secrets point to.
