## Intent

**Problem:** A saved Fit's placements reference wardrobe items by id with no live link back to them. Once a wardrobe item is soft-deleted, editing that Fit falls back to a guessed `'top'` category for the missing placement (a known, deferred bug from Story 3.3), and the Fit detail screen has no way to know a Fit has been left with zero real items — nothing tells the user what happened or lets them recover.

**Approach:** `getFitItems` gains a join against `wardrobe_items` so each placement carries its true `category` and whether its source item is deleted; the edit canvas renders a deleted placement as a selectable, deletable "gap" placeholder (silhouette + label, no photo, no drag/pinch/rotate) at its saved position instead of guessing or rendering nothing, and the Fit detail screen counts live (non-gap) items to show an empty-state prompt when none remain.

## Boundaries & Constraints

**Always:** `getFitItems` embeds `wardrobe_items(category, deleted_at)` in its select and returns `category` and `wardrobeItemDeleted` per placement (soft-deleted rows are still readable under `wardrobe_items_select_own`'s RLS, which has no `deleted_at` condition); `app/new-fit.tsx`'s `loadFit` seeds `PlacedItem.category`/`wardrobeItemDeleted` straight from that response, replacing the `items.find(...) ?? 'top'` guess; `stores/fitBuilder.ts`'s `PlacedItem` gains `wardrobeItemDeleted?: boolean` (unset/false for anything from `addItem`); `CanvasItem` renders a gap placeholder (existing `GarmentSilhouette`, dashed/muted, using `item.category`, no `Image`) when `item.wardrobeItemDeleted`, drops pan/pinch/rotation from its gesture composition for that item but keeps tap-to-select, so the existing selection + floating Delete button (`FitCanvas`'s `removeItem`) can clear it; `FitCanvas`'s existing `capturing` prop (already forces `isSelected: false` for capture) also suppresses the gap's placeholder chrome during capture, so it renders as true empty space in any newly-saved cover, never a baked "removed" glyph — mirrors how ghost slots and the delete button are already excluded from the captured subtree; a re-saved Fit needs no orphan-cleanup change — a gap left in place simply re-persists its existing `fit_items` row (still a valid placement pointing at the same, still-deleted, wardrobe item id), and "deleted" is re-derived from the join on next load, never stored; `app/fit/[id].tsx` calls `getFitItems(fit.id)` and counts placements where `!wardrobeItemDeleted`; a Fit with zero such items renders an empty state (message + "Add item" button routing to `/new-fit?fitId=...`) in place of the cover image, and hides the now-redundant footer Edit button while showing it (Delete stays available); unit tests written before the implementation they cover, per this codebase's established convention.

**Never:** No schema/migration change — `fit_items.item_id`'s `on delete cascade` never fires since wardrobe deletion is a soft `UPDATE`, and category/deleted-status are fully recoverable via the join; no automatic regeneration of a Fit's stored `cover_path` when a wardrobe item is deleted — the baked cover only updates on the Fit's next explicit save, same as every existing cover-staleness case; no change to `saveFit.ts`'s save/orphan-cleanup logic; no changes to the Fits-tab list screen (`app/(tabs)/fits.tsx`) — it already shows only name/thumbnail, no item count; no new interaction beyond tap-to-select-then-delete for a gap (no re-fill/replace-via-catalog affordance).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Edit a Fit with one deleted item among several | `getFitItems` returns one placement whose `wardrobe_items.deleted_at` is set | Canvas seeds that placement as a gap at its saved x/y/scale/rotation; other items render normally | N/A |
| Delete the gap from the canvas | Gap selected, Delete tapped | Removed from `items` store; absent from `fit_items` after next save (existing orphan-cleanup) | N/A |
| Save a Fit that still has a gap | User saves without removing the gap | New cover shows blank space at the gap's position (chrome suppressed during capture); `fit_items` row for it persists unchanged | N/A |
| Open a Fit whose every item was deleted | `getFitItems` returns only `wardrobeItemDeleted: true` placements (or none) | Fit detail screen shows empty state instead of cover, with "Add item" routing to edit | N/A |
| Open a Fit that legitimately still has live items | `getFitItems` returns at least one `wardrobeItemDeleted: false` placement | Cover renders as today, no empty state | N/A |
| No connection (or any error) while loading item count on Fit detail | `getFitItems` throws | Fails open: cover/name/Edit/Delete render exactly as if the Fit had live items, no visible error, no crash; non-connection errors still reported to Sentry | Silent fail-open, not a blocking error screen -- a secondary read's failure must never cost the user the ability to view/edit/delete an otherwise healthy Fit (amended after review pass 1, finding #3 -- see Review Triage Log) |

- Given a Fit with multiple items, when one of those items is deleted from the wardrobe, then the Fit keeps its remaining items and the edit canvas shows a visible, selectable gap at the deleted item's saved position rather than a guessed category or blank render.

## Implementation Notes

- `getFitItems`'s embedded `wardrobe_items(category, deleted_at)` select comes back from the untyped Supabase client's query builder as an array-shaped TypeScript type (no generated `Database` schema in this repo to tell it the relationship is many-to-one), even though PostgREST always returns a single object at runtime for this FK direction. Handled with an explicit `FitItemRow` type and a single documented cast, mirroring `listFits.ts`/`listItems.ts`'s own `as FitRow[]`-style casts rather than fighting the inferred type.
- `app/new-fit.tsx`'s `loadFit` no longer reads from the live `useWardrobeItems()` list to resolve a seeded placement's `category` -- it comes straight from `getFitItems`'s join now, which also correctly recovers the category of a *deleted* item (soft-deleted rows are still queryable under `wardrobe_items_select_own`'s RLS). This removes the `?? 'top'` guess Story 3.3 deliberately left in place and deferred to this story.
- `CanvasItem`'s gap placeholder and gesture restriction are exercised in `fitCanvas.test.tsx` only indirectly, through the props `FitCanvas` passes to a mocked `CanvasItem` (`capturing`, `item.wardrobeItemDeleted`, selectability via the existing generic selection flow) -- `CanvasItem` itself has no dedicated test suite in this codebase (Reanimated/gesture-handler aren't mockable under Jest here), the same limitation already noted for its selection outline and other capture-time chrome. The actual gap silhouette/dashed-outline rendering and drag/pinch/rotate suppression are verified manually on-device (see Verification), consistent with existing precedent in this file.
- Consulted the `ui-ux-pro-max` skill before finalizing the gap/empty-state visuals: no icon on either surface (matches this app's existing `GhostSlot`/`wardrobe.tsx`/`fits.tsx` empty-state precedent, keeps the monochrome system restrained, and avoids any temptation to reach for the oxblood accent outside its reserved CTA/item-name use); the gap's hitbox inherits `CanvasItem`'s existing `MIN_TOUCH_TARGET`/`hitSlop` handling, so no new touch-target work was needed. No text label was added to the in-canvas gap itself -- at typical item sizes there's no room for one without colliding with a neighboring item, and the dashed outline + muted category silhouette (plus the Delete affordance once selected) already read as "something was here, now empty" without one.
- `app/fit/[id].tsx`'s new item-count read uses `useQuery` (not a one-shot effect) since, unlike `new-fit.tsx`'s Zustand-seeding effect, this is cached read state the component renders from directly on every visit -- matches this codebase's established "useQuery for all reads" convention. Its failure is treated as a full-page blocking error (reusing the exact same pattern as the adjacent `isListError` branch) rather than failing open, since silently assuming "not empty" on a fetch failure could show a stale cover for a Fit that's actually empty, and failing closed (assuming "empty") could just as wrongly hide real remaining items -- neither guess is safe, so it surfaces the failure with a Retry instead. Caught one bug during implementation: `getFitItems` throws its own classified `FitError`, not the raw Supabase error `useFits`'s queryFn lets through, so the existing `isNoConnectionError` helper doesn't recognize it -- fixed by matching `app/new-fit.tsx`'s own `instanceof FitError && error.kind === 'no_connection'` check instead, caught by the new offline-retry test before it shipped.

## Design Notes

The gap placeholder and the Fit detail empty state are both new, user-visible surfaces in an app with an established minimalist token system (see `GhostSlot.tsx`'s restrained hairline-tint/badge treatment and `colors.ts`'s existing tokens). Consult the `ui-ux-pro-max` skill's local guidance before choosing the exact gap visual (icon, dash pattern, opacity) and the detail-screen empty state's layout — reuse existing tokens (`border-hairline`, `ink-secondary`, `surface-raised`) rather than introducing new colors, and keep microcopy in this app's established tone (short, complete sentences, no exclamation marks): e.g. "Item removed." rather than "Oops, an item is gone!". The Fit detail empty state should echo the wardrobe/Fits-tab empty-state pattern (`EXPERIENCE.md`'s "Add your first item." precedent) rather than inventing a new layout language.
