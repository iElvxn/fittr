- (note) sources: docs/phase-1-spec.md (primary, already-distilled Phase 1 spec) and Fittr MVP Requirements.md (ancillary background, full MVP incl. deferred social layer)
- (note) topic scoped to Phase 1 only: wardrobe + outfit loop with accounts and cloud-backed sync, no in-app social; Share = export to iOS share sheet
- (capability) CAP-1 Accounts — intent: user can create and manage an account via Sign in with Apple or email/password, sign out, delete account, with required display name and optional avatar. success: sign up, sign in, sign out, and delete account all complete on a dev build
- (capability) CAP-2 Wardrobe — intent: user can add clothing items from camera or library with on-device background removal, category, auto-detected editable color, and optional name/brand/notes, then view in a filterable grid, edit, or delete any item. success: ten items added from photos in under three minutes by either capture method, background removal acceptable on typical clothing photos laid flat or on a hanger
- (capability) CAP-3 Batch add — intent: user can select multiple library photos at once, or capture several in rapid succession without leaving the camera, and review every item in one shared queue before saving. success: library multi-select and rapid-camera batches both land in the same queue/review screen, each item confirmed individually before save
- (capability) CAP-4 Fits — intent: user can start a Fit from a template that seeds initial item placement, add wardrobe items from any category onto a freeform canvas, freely drag/pinch/rotate/reorder them, then name, save, edit, delete, or favorite the Fit. success: a Fit built from wardrobe items across categories can be freely rearranged, saved, edited, and exported as a share image
- (capability) CAP-5 My Fits — intent: user can browse saved Fits in a grid filterable to All, Favorites, or Worn. success: the My Fits list correctly narrows to just favorited or just worn Fits when filtered
- (capability) CAP-6 Planner — intent: user can assign a saved Fit to a day on a weekly calendar, view/replace/remove that assignment, and see today's planned Fit on Home. success: a week can be fully planned and a Fit marked worn directly from Home
- (capability) CAP-7 Share — intent: user can export a Fit's rendered collage image to the iOS share sheet. success: share produces a correct collage image the iOS share sheet can send onward
- (capability) CAP-8 Sync — intent: the app reads and writes SQLite locally first and reconciles with Postgres in the background, so every wardrobe, Fit, and planner action works offline. success: deleting and reinstalling the app restores all wardrobe, Fit, and planner data from Postgres
- (capability) CAP-9 Privacy — intent: all wardrobe, Fit, and account data stays private to its owner, and deleting an item, Fit, or the account removes the corresponding rows and stored images. success: row-level security rejects cross-user access, and account deletion hard-deletes all of a user's rows and storage objects, then the auth user
- (capability) CAP-10 Measurement — intent: the app emits funnel analytics events and crash reports from first launch so usage and stability are measurable throughout Phase 1. success: a test event reaches PostHog on a dev build and the full signup-through-return funnel can be reconstructed from recorded events
- (constraint) Minimum iOS 17.0, required by the on-device background-removal (subject-lifting) module — rules out supporting older iOS versions
- (constraint) Solo developer on Windows: all native builds run on EAS; development uses an EAS development build on a physical iPhone since Expo Go can't host the background-removal module
- (constraint) Local-first architecture: every read and write targets SQLite; Postgres sync runs only in the background and never blocks the UI
- (constraint) Sync conflicts resolve last-write-wins on updated_at, accepted for single-user/rare-multi-device use; documented as a deliberate simplification, revisit if multi-device use grows
- (constraint) Background removal runs on-device rather than via an API, for cost, privacy, and speed
- (constraint) Category selection is manual in Phase 1 — no AI-based category detection (deferred until it can sit behind a server function)
- (constraint) No Redis, queues, or streaming in Phase 1
- (constraint) Supabase Storage sits behind an ImageStore interface so the storage backend can be swapped later (e.g. S3, R2)
- (constraint) The original photo is discarded once its cutout is confirmed and is never uploaded or retained; a poor cutout is fixed by re-photographing, not reprocessing
- (constraint) No data-export feature in Phase 1 — sync-restore-after-reinstall and account deletion already cover the restore/privacy needs export would have served
- (decision) Non-goal: in-app social entirely — no posts, feed, likes, comments, follows, saves, discover, or notifications; Share means exporting an image to the iOS share sheet only
- (decision) Non-goal: usernames are collected at onboarding but not surfaced in Phase 1 UI beyond profile settings; no username-based search
- (decision) Non-goal: AI-based clothing category detection
- (decision) Non-goal: outfit recommendations or an AI stylist
- (decision) Non-goal: weather-aware outfit recommendations
- (decision) Non-goal: commerce, affiliate shopping, or marketplace features
- (decision) Non-goal: Android and web platforms
- (decision) Success signal: Phase 1 validates 'people will repeatedly use a digital version of their wardrobe to create, save, plan, and share outfits' when five test users can explain what Fittr is, why to add clothes, how to make a Fit, and why to come back, and a TestFlight cohort's two-week funnel (signup to 5 items to first Fit to second Fit to worn/planned to returned the following week) shows repeated use past initial wardrobe setup
- (question) Which additional Fit templates beyond 'Top + Bottom + Shoes', 'Layered Outerwear', and 'Blank canvas' should ship (CAP-4) — finalize once the canvas is built and a few Fits have been made by hand
