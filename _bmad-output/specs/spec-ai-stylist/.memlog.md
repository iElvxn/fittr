- (direction) Source: 2026-09-26..10-01 design conversation + memory note project-ai-stylist-idea; user asked for a detailed spec; express distill chosen (input rich).
- (decision) Why: vision + differentiator; competitors (Cloey swipes, Whering random Dress Me) learn weak signals or feel random; fittr has wears, planner, swaps as stronger signals.
- (capability) CAP-1 Occasion request: user describes an occasion/need in free text or chips and gets 3 Fits built only from their own items, each with a one-line reason.
- (capability) CAP-2 Curate mode: user asks for surprise/varied looks from a prompt; results are weighted-random, diverse across the 3 Fits, and avoid recently suggested items; Shuffle re-samples.
- (capability) CAP-3 Style requests: user picks a preset style chip or types a free-text style (incl. blends and unknown styles) and results adhere to that style's definition.
- (capability) CAP-4 Pins: user can require items (tap from closet/item detail, or describe in text); every returned Fit contains every pin; ambiguous text pins ask the user to choose.
- (capability) CAP-5 Exclusions: user can exclude items/types per request and set persistent never-suggest rules; excluded items never appear.
- (capability) CAP-6 Personalization: suggestions reflect the user's taste learned from worn, saved, liked, swapped and dismissed Fits plus explicit onboarding prefs; cold start works from prefs + request alone.
- (capability) CAP-7 Act on results: save as Fit, plan for a day, open in builder, swap one piece, more like this, dismiss; each action is logged as feedback.
- (capability) CAP-8 Honest coverage: when the closet cannot satisfy a style/pin/occasion, the user is told and offered the closest take; the system never labels a weak Fit as on-style or invents items.
- (capability) CAP-9 Item understanding: every item gets rich attributes and an image embedding automatically after add, plus per-style affinity scores; existing items are backfilled.
- (capability) CAP-10 Visual check: final outfits are reviewed by a vision model looking at the item images; weak pieces are swapped or the outfit dropped.
- (capability) CAP-11 Evals and logging: an offline harness scores the pipeline on fixture closets against a category-valid random baseline; every request logs inputs, candidates, outputs, tokens, cost, latency.
- (capability) CAP-12 Usage limits: per-user daily request cap enforced server-side; over-limit returns a clear state.
- (constraint) Only the user's own items: model picks item IDs from a server-supplied candidate list; output IDs validated against candidates and ownership; never invent items.
- (constraint) Pins are hard constraints enforced in code (locked before generation, validator rejects missing pins); 100% adherence required.
- (constraint) LLM/embedding keys live only in Supabase Edge Function secrets; allowed under NFR9 trust-boundary/secret exception, recorded explicitly.
- (constraint) Edge Functions read with the caller's JWT so RLS scopes all reads to that user; service role only for writing server-owned tables.
- (constraint) NFR7 no Redis/queues: async tagging via DB webhook + status column swept by pg_cron; no pgmq.
- (constraint) Server-owned tables (item_attributes, item_style_scores, stylist_requests) have RLS select-own and no client write policies.
- (constraint) Minimum closet to unlock: at least one top, one bottom, one shoes.
- (constraint) UI: named Stylist in the serif, no chat UI, no sparkles/AI cliches; follows redesign v2 palette.
- (constraint) Item photos go to a third-party model API; Stylist onboarding discloses this before first use.
- (constraint) Randomness lives in code (weighted sampling), not in the LLM; item order shuffled per call to counter position bias.
- (constraint) Build baseline-first: each layer after v0 ships only if the eval shows it helps (or is cheaper at equal quality).
- (decision) Send photos: 400px webp thumbs ~225 vision tokens each; ~30 candidates ~7k tokens; whole 100-item closet ~22.5k; WebP supported, up to 600 images/request.
- (decision) Pipeline: intent parse -> SQL hard filters -> per-slot scoring (style, taste, attribute fit, freshness, penalties) -> best (top-K) or curate (softmax sampling + MMR) -> LLM assembles with images, concept/anchor-first schema -> validator + 1 retry -> visual check -> log.
- (decision) Style library: style cards (definition, key pieces, palette, fabrics, patterns, silhouette, formality, rules, vibe + anti-vibe text, reference images); centroid from reference image embeddings; item_style_scores precomputed at tagging; unknown styles get an LLM-drafted card cached for reuse.
- (decision) Style match = differential vibe minus anti-vibe affinity (per Loom paper) blended with attribute match.
- (decision) Taste vector: weighted mean of item embeddings from worn(3)/saved(2)/liked(1) minus dismissed; plus nightly LLM taste summary; plus 3-5 most similar past Fits as examples.
- (decision) Cross-user collaborative filtering does not apply (items unique per user); image embedding space is the shared space.
- (decision) v0 baseline: full closet thumbnails + existing fields straight to the LLM with structured output, validator, logging, eval harness. v1 tagging+filters+retrieval. v2 personalization. v3 style library. Visual check gated by eval.
- (decision) Visual check uses item images per outfit (no server-side collage render in scope).
- (decision) Entry points: Home when nothing planned, Planner day sheet, Item detail 'Style this piece', later passive daily suggestion on Home.
- (assumption) Weather is new to the app; assumed client fetches it and passes to the function (keeps location off the server).
- (assumption) Transparent cutouts may need flattening onto a neutral background before sending; to verify in v0.
- (assumption) Embeddings: FashionCLIP-class model via hosted inference endpoint (Claude has no embeddings API).
